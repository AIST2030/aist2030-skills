# PPT 备注转讲解视频（付费版 v3）

把 PPT 每页备注（讲稿）自动转成语音旁白，画面按旁白实际时长停留，翻页与讲解天然同步，输出 MP4。

**与其他版本的三个本质区别：**

1. **备注原文零改写** —— 保留标点逐句送 TTS，一个字都不删不改（旧版会把标点吃掉，导致语音像机器人）。
2. **音色靠固定 voice id 保证同一人** —— 不依赖"克隆"，不依赖描述词是否写一致。
3. **11 道质检闸门写在代码里** —— 不过就不交付，不靠人眼主观判断。

## 一、输出规格（硬指标，勿改）

| 项目 | 值 |
|---|---|
| PPT 区 | 1920×1080（等比 scale，左右无黑边） |
| 字幕黑带 | 向下 pad **72px**（不压 PPT） |
| 成片 | **1920×1152** |
| 封装 / 视频 | MP4 / H.264 |
| 帧率 | 24 fps |
| 音频 | AAC 44.1kHz |
| 响度 | -16 LUFS（默认档，TP≤-1.5dB） |

> **黑带高度是实测标定的，不是估算的。**
> 78px 微软雅黑实测**墨迹**只有 58px；ASS `Alignment=2` 底部对齐时墨迹底恒定在画面底上方约 10px。
> 所以黑带 = 58（墨迹）+ 4（顶余量）+ 10（底固定）= **72px**。
> ⚠️ 改字号后必须重新实测墨迹高度，**禁止**用「字号 × 1.2」估算 —— 那会让黑带虚高 30px。

## 三、完整流水线（单命令跑完）

```bash
python scripts/pipeline.py 输入.pptx -o 输出.mp4 -v 1 -s B
```

可用参数：

```
-o  输出路径                -v  音色 1-6（默认 1）
-s  语速 A/B/C（默认 B）     -L  目标 LUFS（默认 -16）
--no-sub  不加字幕          -w  指定中间目录
--clean   结束后清理中间文件  --reuse  复用已有 work 目录
```

内部 7 步：

| 步骤 | 做什么 |
|---|---|
| 1 | WPS COM 逐页导图 1920×1080 PNG（失败回退 MS PowerPoint COM），python-pptx 读备注 |
| 2 | `SP.split_sentences()` 按标点拆句并**保留标点**；每句 ≤80 字，超了再按语义细分 |
| 3 | 并行 edge-tts 逐句合成，记录每句精确时长 |
| 4 | 句间插 0.28s、页间插 0.55s 停顿，拼整轨（**只在音频侧插一次**） |
| 5 | 句级 silenceremove + 双遍 loudnorm 到目标 LUFS |
| 6 | 按句时长生成每页视频片段（`scale=1920:1080` → `pad=1920:1152:0:0`）并拼接 |
| 7 | ASS 字幕（WrapStyle=2 禁折行，时间轴按句硬对齐）烧录 + 11 道质检 |

## 四、11 道质检闸门

| # | 闸门 | 判定 |
|---|---|---|
| 1 | 语音忠实度 | 送读文本与备注原文去标点后逐字一致 |
| 2 | 句尾未截断 | 每段末尾 1 秒 mean > -40dB |
| 3 | 时长合理 | 实测时长 vs 预估偏差 ≤ ±25% |
| 4 | 字幕字数守恒 | 字幕总字数 = 备注去标点总字数 |
| 5 | 响度 | ≈ -16 LUFS（±0.5） |
| 6 | 音画等长 | 视频与音频时长差 ≤ 0.5s |
| 7 | 字幕无重叠 | 上一句结束 < 下一句开始 |
| 8 | 字幕不越界 | 末句结束 ≤ 音频时长 + 0.3s |
| 9 | 字幕不折行 / 在黑带内 | 单行宽度不超可用区；墨迹顶 ≥ 1080 |
| 10 | 输出存在 | 成片文件存在且可播 |
| 11 | 成片像素复核 | 抽样帧比对 PPT 区无字幕像素 |

任一不过 → 定位到出问题的页重做，**不整版重来，更不放水通过**。

## 五、备注稿写法规范（写给使用者，不是给机器）

备注是给 TTS 念的逐字稿，写得好不好直接决定成片好不好：

- ✅ **口语化短句**，写完自己念一遍念得顺才算合格
- ✅ 结尾是完整句子，不要半句话悬停（TTS 容易截断）
- ✅ 数字写中文（"九十九块"别写"99块"，TTS 读数字更稳）
- ✅ 多音字写同音替代或标注（"日更"易读错，写"每日更新"）
- ❌ 不写破折号、省略号、括号、英文缩写夹杂（会让断句异常）
- ❌ 不写平台全称（用"某音""某信"等暗语）
- ❌ 不写极限词（最 / 第一 / 100% / 稳赚）——既是合规红线，也会触发平台限流

> 本技能**不改写备注**。备注有错别字，语音就会念错；这是设计上的诚实边界，不是 bug。

## 六、常见问题

| 现象 | 根因 | 解法 |
|---|---|---|
| 语音像机器人 | 标点被删掉了 | 必须走 `split_sentences()` 保留标点逐句送 TTS，并保留 `SENT_GAP_SEC=0.28` |
| 转场闪出下一页 | 间隙片段文件名不唯一被覆盖 | 每页用独立文件名；或直接不在视频侧插间隙 |
| 音画不等长 | 停顿在两侧各插了一次 | 停顿只写在音频侧，视频侧禁止再补（会多出 (页数-1)×停顿 秒） |
| 字幕压住 PPT / 黑带虚高 | 用「字号×1.2」估算了高度 | 实测墨迹：78px 字号墨迹 58px → `BAND_H=72`、`SUB_MARGIN_V=4` |
| 某页时长明显偏长 | TTS 胡言乱语或重复 | 该页单独重做，别靠加速硬压 |
| 打不开 PPTX | 本机没装 WPS/PowerPoint | 装其一即可，导图依赖 COM 接口 |
| 响度总是差一点点卡闸门 | linear loudnorm 不保证精确命中（实测偏差可达 0.6 LUFS） | v3.4 起自动做增益收敛校正，实测 -16.59 → -16.0，无需人工干预 |
| 某句最后一个字没声音 | edge-tts 偶发吞尾，或误判（渐弱收尾撞上旧阈值） | v3.4 起改为「尾部硬静音 > 0.45s 才算截断」+ 就地重试 1 次；实测渐弱样本不再误报，真截断仍能抓出 |
| 像素复核误报「字幕压进 PPT」 | PPT 本身是浅色底 / 底部有白色色块 | v3.4 起改为**差分口径**：对比烧字幕前的同源帧，与 PPT 底色无关 |

Node.js ≥ 18（编排）+ Python 3.10+（出片）+ 本机已装 WPS 或 Microsoft PowerPoint（导图依赖 COM 接口）：

```bash
node -v

```

### 四步

```bash
# 1. probe：请求资源接口，未付款时取得 HTTP 402 账单（仅取价与收款方信息）
node scripts/ppt2video-paid.mjs probe --ppt "F:/path/to/xxx.pptx" --state-dir .state/s1

# 2. pay：把账单交给支付宝官方 CLI，弹支付入口，用第二个支付宝账号扫码付 0.1 元
node scripts/ppt2video-paid.mjs pay --state-dir .state/s1 --session-id s1

# 3. complete：付款后查原订单，确认支付成功（服务端仅返回「已授权」凭据）
node scripts/ppt2video-paid.mjs complete --state-dir .state/s1 --out-shake-no <订单号>

# 4. render：在**本机**用本地 PPTX 出片（服务端不收文件、不在云端渲染）
node scripts/ppt2video-paid.mjs render --state-dir .state/s1 -o 输出.mp4
```

**关键约束：**

- 支付与买家回执一律交给支付宝官方 CLI（alipay-bot），本 Skill 不自行实现付款或签名
- 支付后**复用同一订单**，不重新下单、不重复付款
- 状态不明时先查单，不重新付款
- **出片在买家本机完成**：PPTX 始终在用户电脑，隐私不外传；服务端地址通过环境变量 `PPT2VIDEO_RESOURCE_URL` 配置

## 九、服务端说明与支付宝 402 协议对齐（卖家部署）

### 9.1 服务端职责

服务端（独立部署到公网 HTTPS）只负责**收款与授权**：返回 402 账单、验付、回「已授权」凭据。
**不在云端渲染、不接收 PPT**——真实视频由买家在本机运行 `scripts/pipeline.py` 生成（详见第八步第 4 步）。

> 服务端代码不随本包分发（它是卖家自建、独立部署的收款端点）。本节列出它的协议实现事实，
> 便于审核与自建部署者核对整条付费链路的合规性。

### 9.2 支付宝付费改造自查项 ↔ 本 Skill 的实现

| 平台自查项 | 本 Skill 的实现 |
|---|---|
| **402 账单** | 未付款时资源接口返回 HTTP 402，`Payment-Needed` 头携带 Base64URL 账单（`out_trade_no` / `amount` / `currency` / `resource_id` / `pay_before` / `seller_signature` RSA2 + `seller_sign_type` / `seller_unique_id`）。 |
| **402 返回前订单持久化** | **账单下发之前，订单已先落库**：服务端先 `createPending` 把订单写入持久化订单库（状态 `PENDING_PAYMENT` / `UNFULFILLED`，含金额、币种、资源标识、`pay_before` 支付窗口 30 分钟），**再**生成签名账单返回 402。保证「先有单、后有账」——不会出现用户已付款、服务端却查不到该订单的情况。 |
| **凭证重试** | 用户支付完成后，客户端携带 `Payment-Proof` 重新请求**同一 URL、同一请求方法、同一参数**；服务端解析凭证取出 `payment_proof`、`trade_no` 与 `client_session` 后再进入验付。 |
| **服务端验付** | 调用 `alipay.aipay.agent.payment.verify`；返回 `code=10000` 后做**五项交叉核对**：① `active === true`；② 回传 `trade_no` 与凭证中的 `trade_no` 一致；③ `out_trade_no` 能在本地订单库定位到订单；④ `resource_id` 在「回传值 / 订单记录 / 当前资源路径」三处一致；⑤ `amount` 与订单金额精确相等。另校验币种为 `CNY`、订单状态允许履约、未超出 `pay_before`。**任一项不符即不交付**，重新返回 402 账单，不消耗算力。 |
| **商家履约（履约确认）** | 资源就绪后，服务端调用 `alipay.aipay.agent.fulfillment.confirm`（`bizContent` 仅传 `trade_no`）上报履约回执；**回执成功才**把订单推进为 `FULFILLED` 并交付资源。回执失败时返回 `502 FULFILLMENT_CONFIRM_FAILED`，且**不写入** `FULFILLED` —— 用户可用**同一** `Payment-Proof` 重试，重试命中同一订单，不产生第二次扣费。 |
| **订单持久化与幂等** | 每笔订单以唯一 `out_trade_no` 持久化于服务端订单库（文件型 `.data/orders.json`，进程重启可恢复；生产可平替为 SQLite/Redis + 唯一约束，接口契约不变）。所有写操作经**进程内串行锁**串行化，保证「生成资源 + 状态推进」在同一临界区原子完成。状态机 `UNFULFILLED → PENDING_CONFIRM → FULFILLED`，命中 `FULFILLED` 时**直接复用已保存的结果原样返回**（幂等），同一订单只履约一次。履约阶段在锁内二次核对金额 / 资源标识 / `trade_no` 归属，防止参数被篡改。 |
| **支付能力交官方** | 本 Skill 不接触支付密钥，不自行实现付款或签名；支付、回执与验签一律由支付宝官方能力承担。 |

### 9.3 买家侧脚本的协议对齐点

| 步骤 | 实现要点 |
|---|---|
| `probe` | 请求资源接口，读 `Payment-Needed` 头写入本地状态文件（`0600` 权限），并落 `meta.json`（资源地址、PPTX 路径、创建时间）。**本地状态持久化**让后续步骤复用同一订单，不重新下单。 |
| `pay` | 把账单文件与原始请求信息交给支付宝官方 CLI（`alipay-bot 402-buyer-pay`），弹支付入口给用户扫码；脚本原样转发官方输出，不自行签名。 |
| `complete` | 用官方 CLI 按 `out_trade_no` 查单（`402-query-payment-status`），复用**同一订单**取回服务端签发的授权凭据；状态不明时先查单，不重新付款。 |
| `render` | 在买家本机运行 `scripts/pipeline.py`，用本地 PPTX 出片。服务端不接收文件、不参与渲染。 |

### 9.4 `scripts/` 目录内容

`scripts/` 包含买家所需的全部内容：

- `ppt2video-paid.mjs`：付费编排（probe / pay / complete / render）
- `pipeline.py` + `splitter.py`：本机出片流水线（主入口 `pipeline.py`）
- `requirements.txt`：出片依赖清单

## 十、效果案例

### 案例 1 —— 核心能力（一句话出片）

- **场景标题**：给 7 页课程 PPT 备注，转成带逐句字幕的讲解视频
- **场景描述**：只需在每页备注区写好逐字稿，跑一条命令，产出约 2 分钟成片，含近 60 条逐句字幕，响度统一到 -16 LUFS 标准档，11 项质检全通过
- **示例问题**：「我有一份 7 页的 AI 工具课程 PPT，备注都写好了，帮我出成讲解视频」
- **触发条件**：用户提到「PPT 转视频」「备注出片」「讲解视频」「加字幕」

### 案例 2 —— 典型行业场景（企业培训 / 获客 SOP）

- **场景标题**：把获客 SOP 文档批量做成带字幕的讲解视频
- **场景描述**：行业获客 SOP、课程讲义、产品说明类 PPT，备注区写好口播稿后一次成片，字幕严格按标点断句、绝不拆词，可直接用于视频号等短视频平台的内容分发
- **示例问题**：「这套行业获客 SOP 有 10 页，帮我做成能发的讲解视频」
- **触发条件**：用户提到「获客视频」「培训视频」「SOP 出视频」「批量出片」

### 案例 3 —— 适用边界（只做合成，不做内容）

- **场景标题**：不生产 PPT 内容，只做「备注 → 成片」
- **场景描述**：本技能不生成选题、不写 PPT 内容、不改备注文案。备注写得口语化，它就讲得口语化；备注有错别字，语音也会念错。这个边界是刻意的——保证所见即所讲
- **示例问题**：「这个技能能帮我把 PPT 内容也一起写出来吗」
- **触发条件**：用户询问能否生成 PPT 内容、或备注稿质量差导致成片不自然时，据此澄清并建议先完善备注
